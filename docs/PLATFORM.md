# Platform investigation

Research checked on 2026-10-10. This describes API/upstream evidence, not physical hardware certification. Runtime results are recorded separately in TESTING.md.

## Awake computer versus usable display

[Apple’s PreventUserIdleSystemSleep documentation](https://developer.apple.com/documentation/iokit/kiopmassertiontypepreventuseridlesystemsleep) permits the display to dim/sleep and explicitly allows sleep for lid close, Apple-menu sleep, low battery and other reasons. Guillotine uses exactly this assertion. It does not request PreventUserIdleDisplaySleep, declare user activity, generate synthetic input or turn brightness to zero. Keyboard backlight inactivity policy is left to macOS; no supported force-off API is used.

[Apple’s power-source notification API](https://developer.apple.com/documentation/iokit/1523868-iopsnotificationcreaterunloopsou) supplies event-driven updates. `IOPSGetProvidingPowerSourceType` classifies the source actually supplying the computer, including AC for battery-less desktops. Guillotine never uses `IsCharging` to decide whether external power is available. It treats UPS/battery/unknown states as ineligible. Events and transitions are synchronous on the main actor, with an additional power read before and after assertion creation. OS delivery has finite latency; “immediately” means in the power notification callback, not a hard real-time electrical guarantee. macOS may coalesce notifications; software cannot react before the OS reports a transition.

## Lid closed: what works, and what is not promised

[Apple’s closed-lid M3 display setup](https://support.apple.com/en-us/117373) specifies external power, displays, and external keyboard/mouse or trackpad. The exact display limits depend on the Mac model. [Apple Silicon accessory approval](https://support.apple.com/en-us/102282) can also affect closed-lid peripherals. This is the supported route, leaving normal lid and lock behavior under macOS control.

A hardware HDMI/USB-C **EDID emulator/dummy plug** may substitute a detected display without a physical panel. That is an inference from the display requirement, not an Apple guarantee or an adapter certification. Test your hardware, OS, adapter and capture stack. A software virtual display may provide pixels for capture yet fail to engage native clamshell operation. Guillotine reports “setup must be verified” rather than inferring success from screen enumeration. Desktop Macs have no lid constraint.

An actual software route used by current upstream tools is privileged `pmset disablesleep 1`: [Amped implementation and documented behavior](https://github.com/gustaferiksson/amped) and [Amphetamine’s Apple Silicon Power Protect](https://github.com/x74353/Amphetamine-Power-Protect). The latter documents power-transition problems and a privileged script/sudoers installation. [Apple’s pmset source](https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.m) maps `disablesleep` to system-wide `SleepDisabled` and saves system power settings; the local pmset manual requires root for settings changes. This is not a lid-close-only assertion. Upstream reports are evidence of a possible technique, not proof across current Apple Silicon/Intel models.

Guillotine deliberately does **not** ship that override. Implementing a safe variant would need a signed, authenticated privileged service, independent AC notifications, a short renewable lease, durable original-state journal before mutation, recovery at service startup, and restoration on invalidation/expiration. Even then a shared boolean has no ownership/CAS token: a user or another utility writing the same value during the lease cannot be distinguished from the helper’s write. Broad sleep suppression can also alter lid-triggered sleep/locking semantics. Guaranteeing all of the requested ownership and normal authentication behavior is not established by the evidence. No untested privileged component is presented as safe or reliable.

No SIP changes, kernel extensions, synthetic input, hidden sudoers permissions, private clamshell APIs or persistent power controls are included. This means **software-only closed-lid, no-display operation is not implemented**. The delivered working portion is idle-system-sleep prevention plus safe event-driven AC gating; native clamshell operation relies on a separately validated external-display setup.

## Remote compatibility

| Stack | Upstream evidence | Conditions and limits |
| --- | --- | --- |
| SSH / Remote Login | [Apple Remote Login](https://support.apple.com/guide/mac-help/allow-a-remote-computer-to-access-your-mac-mchlp1066/mac) | Awake system and reachable network; no display. FileVault pre-login and network policy are unchanged. |
| macOS Screen Sharing | [Apple Screen Sharing](https://support.apple.com/guide/mac-help/share-the-screen-of-another-mac-mh14066/mac) | High Performance sessions offer virtual displays on compatible Apple Silicon/macOS 14+ systems. A virtual desktop does not certify clamshell behavior. Standard VNC and Intel setups need separate tests. |
| Sunshine host / Moonlight client | [Sunshine installation](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2getting__started.html), [macOS capture implementation](https://github.com/LizardByte/Sunshine/blob/master/src/platform/macos/display.mm), [host permission checks](https://github.com/LizardByte/Sunshine/blob/master/src/platform/macos/misc.mm) | Experimental native arm64/x86_64 host; upstream lists no gamepad support on macOS. Capture enumerates display devices. Sleep/close can remove the source or stall frames; configure a separate tested graphical surface if necessary. Host permissions remain its responsibility. |
| Vibepollo | [Nonary upstream README](https://github.com/Nonary/Vibepollo), [getting started](https://github.com/Nonary/Vibepollo/blob/master/docs/getting_started.md), [macOS workflow](https://github.com/Nonary/Vibepollo/blob/master/.github/workflows/ci-macos.yml) | Windows-focused features plus Linux beta are documented. macOS workflow code exists, including both architectures, but install text names Sunshine. Workflow existence and inherited docs do not establish an available macOS Vibepollo release. Verify artifacts, version, permissions and successful capture before relying on it. Other forks differ. |
| Third-party virtual displays | [BetterDisplay upstream](https://github.com/waydabber/BetterDisplay) | Upstream supports headless graphical desktops. Guillotine neither installs nor alters these displays, and does not certify them for lid-close operation or a streaming host. |

The Sunshine source lists online displays and creates a capture session for a chosen display. This supports requiring a capturable surface; it does not establish that every sleeping physical display continues producing frames. A successful SSH session proves only system/network liveness. For video acceptance, compare a visibly changing clock or animation on the client, then verify input and lock/unlock. Merely connecting or seeing a stale frame is insufficient.

On the development host, `pmset -g assertions` showed a running **Vibepollo** process with a `PreventUserIdleDisplaySleep` assertion named “Vibepollo is streaming the display.” This is direct evidence that this particular installed build runs on macOS, and that its streaming policy can hold the display awake. It does not establish public artifact availability or successful client capture with the physical display asleep. Guillotine leaves that assertion and streaming process alone. A display cannot be promised to idle-sleep while the streaming host itself prevents it; configure/test the host separately if it exposes that option.

## Permissions, minimum OS and distribution

macOS 13+ supplies `SMAppService.mainApp` for launch at login. Carbon `RegisterEventHotKey` works across foreground apps without broad keyboard monitoring. It is not an escape mechanism from a lock screen and may be suppressed by Secure Input or OS-reserved shortcuts. A registration error blocks activation until an available shortcut is configured. Key labels describe US physical key positions.

The app is unsandboxed and hardened-runtime capable. It has no entitlements granting private APIs or remote access, no helper, and no network code. Local builds can be ad-hoc signed. Public binary distribution should use Developer ID signing and notarization. Apple Silicon and Intel are built from the same public APIs; build success does not imply Intel hardware verification.
